# Authority UTXO — 権限を「二重に使えないコイン」にする

2026-11-16 設計 v0.4（v0.3 は実装済み・REDTEAM_V03 で窓の強さを金額化）。仮説であり、新規性・安全性は未実証。

## 一行で

Bitcoin は「お金の二重使用」を、管理者なしの合意で止めた。
本設計は「**AIに渡した権限の二重使用・水増し**」を、同じ合意で止める。さらに Bitcoin に無かった
「**途中の委任者が、自分の下の枝だけを取り消し、残りを取り戻す**」を、ルール（スクリプト）として強制する。

## 狙う差分（ZKM が将来課題とした所）

ZKM v0.1.0-draft は「元の委任者が全枝を止める」方式で、途中の委任者による枝ごとの失効を将来課題としている（RESEARCH_QUESTION.md 参照）。
本設計の主張候補は次の1点に絞る：

> **委任の木のどの祖先も、自分より下の1枝だけを、他の枝を止めずに失効させ、その未使用枠を二重計上なく自分へ回収できる。
> この保存則（発行量 = 消費 + 破棄 + 未使用）と縮小則（子 ⊆ 親）を、共有管理者ではなく BSV のスクリプト検証と UTXO の一回消費で強制する。**

## 仕組み

1. **権限 = UTXO。** 1つの出力が「利用枠 n 回・操作ビット集合 P・期限 T・祖先鍵の根 R」を持つ。値（satoshi）とは別に、枠はスクリプト内の状態として持つ。
2. **委任 = 分割取引。** 親UTXOを消費して子UTXOを作る。コベナント（OP_PUSH_TX で自分を消費する取引を検査する手法）で次をスクリプトが強制する：
   - 子の枠の合計 ≤ 親の枠（保存則）
   - 子の P は親の P の部分集合（`P_child AND P_parent == P_child`）、子の T ≤ 親の T（縮小則）
   - 子の出力も同じスクリプト型（権限が型の外へ漏れない）
   - 子の R = 親の R に委任者の鍵を足したもの（祖先リストのコミット）
3. **使用 = 消費取引。** 実行者が1回分を消費し、残りを同じ型の出力へ戻す。サービス側は消費取引（＋SPV証明）を見てから API を実行する。
4. **枝の失効＋回収 = 祖先による奪還。** 各出力は「祖先 i の鍵による署名＋祖先リストの包含証明」でも消費できる。奪還取引は対象UTXOを祖先自身の権限UTXOへ戻す。
   - 枝の残枠は1回の UTXO 消費で移るので、二重計上が構造的に起きない。
   - 兄弟枝の UTXO には触れないので、無関係な枝は止まらない。
   - 使用と奪還が競合したら、祖先が必ず勝つ（v0.2 の遅延の非対称。v0.1 の「先着」は反証で撤回）。

## v0.2 の修正（反証への回答）

- **競合は「先着」ではなく「祖先が必ず勝つ」非対称にする。** 保有者の使用・再委任は、消費取引の nSequence / nLockTime を preimage で検査し、遅延 D を課す。祖先の奪還は遅延なし。遅延中は祖先が確定的に勝つ（BIP-345 金庫と同じ形）。BSV は CLTV/CSV を NOP に戻しているので、opcode ではなく preimage 検査で書く。
- **奪還出力にも縮小則・保存則を掛ける。** 奪還取引の出力は「奪還した祖先 i を末尾とする祖先列（R の接頭辞）」「P・T は元の枝以下」「枠は元の枝の残枠と等しい」をスクリプトが強制する。奪還で権限を広げたり、枠を増やしたりできない。
- **祖先列は接頭辞として証明する。** 包含（Merkle）ではなく、祖先鍵列そのもののハッシュ連鎖 R_k = H(R_{k-1} ‖ pk_k) を使い、奪還時は i 番目までの列を開示して R の接頭辞であることを示す。兄弟鍵や内部ノードを祖先に偽装できない。
- **祖先鍵は 2-of-3 などのしきい値にできる形にする。** 盗難そのものは消せない（残る信頼）。
- **ZKM との差は「秘匿」ではなく「回収」。** ZKM の将来案は秘匿したまま下位木を殺すハンドル。本設計は透明な台帳で、未使用枠を祖先の権限UTXOへ保存則つきで戻す。秘匿は v0.2 でも扱わない。

## v0.3 の修正（時刻遅延の撤回 → 作業量で測る遅延）

v0.2 は nLockTime で遅延を作ったが、nLockTime は「この時刻より前は無効」でしかなく、保有者は過去の時刻を選べる。BSV には相対時間（CSV）も無い。よって**時刻の値で遅延を作る方式は原理的に無効**（X01/X02/X05/X07）。

代わりに、**遅延を「実際に積まれたブロックの作業量」で測り、それをスクリプト自身が検証する。**

1. **使用・再委任は2段階。** 保有者はまず「予告」取引で権限UTXOを『予告中』状態へ移す（中身＝何をするか、のハッシュを記録）。
2. **予告中は祖先がいつでも奪還できる**（遅延なし）。
3. **確定は、予告取引の後に K 個のブロックが積まれた証明を付けたときだけ。** 確定取引のスクリプトは、preimage の outpoint から予告取引の txid を取り出し、(a) txid がブロックヘッダ h0 の Merkle 根に含まれる証明、(b) h0 から h_K までのヘッダが前ハッシュでつながる、(c) 各ヘッダのハッシュが難易度の下限以下、を自分で検証する。
4. 下限難易度はスクリプトに固定する。偽のヘッダ K 個を作るコスト＝下限難易度で K ブロック掘るコスト。これを「祖先が気づいて奪還するまでの時間」の代わりにする。

狙い: 時計を信用せず、マイナー全体の作業量で「祖先が先に動ける窓」を作る。BSV は大きなスクリプトを許すので、ヘッダ検証をスクリプト内でできる（BTC では現実的でない）。

同時にふさぐ穴: 状態の数値（d・n・P・T）は符号付き範囲で検査する（X06/X22）。時刻モード混同は、時刻を使わなくなるので消える。

先行: sCrypt はブロックヘッダをスクリプトで検証する手法を公開している。ヘッダ検証そのものは新規ではない。主張するのは「委任木の祖先優先の失効窓を、時計なしに作業量で強制する」組合せだけ。

## v0.4 — 失効窓の強さ＝BSV 自身の K 確認と同じ

REDTEAM_V03 の実測: スクリプトは実チェーンを見られないので、攻撃者は自作の偽ヘッダ（浮遊ヘッダ）で確定できる。防げるのはコストだけ。下限をメインネット難易度（高さ 975,655）に置くと、K=2 の偽造コストは (K+1)=3 ブロック分の採掘報酬 ≒ **135.8 ドル**（3.125 BSV×3、14.48 USD/BSV、2026-11-15）。

これは欠陥ではなく性質として書く: **失効窓の安全性は、BSV で K 確認を待った取引の安全性と同じ**（どちらも K+1 ブロック分の作業で覆る）。チェーン自身より強くはできず、弱くもない。

- **パラメータ化:** K と下限ターゲットは権限UTXOの発行時に決め、コード部に固定する（子も同じ値を継ぐ）。
- **K の決め方:** 失効窓が守る価値 V に対し `K+1 ≥ V ÷ (1ブロックの報酬の時価)`。例: 1ブロック≒45.3ドルなので V=1万ドルなら K≈220（約37時間・ヘッダ約17.7KB）。K=73 は約3,350ドル分（約12時間）。BSV は大きなスクリプトを許すので K を数百にできる（BTC ではできない）。
- **正直な経路の窓:** 偽造しない保有者は本物の K ブロックを待つので、祖先には約 K×10 分の見張り時間がある。
- **下限ターゲットの下げ幅:** 難易度は変動するので、下限は現行の 1/4 程度にし、その分 K を増やす。

## 残る信頼（「信頼不要」と言わない）

- BSV の合意（計算力の多数が正直）と、スクリプト実装の正しさ
- サービス側が「消費の確定を見てから実行する」こと。台帳の一回消費は外部 API の一回実行を保証しない（実行後・記録前の停止）
- 鍵管理。祖先鍵が盗まれると、その祖先より下を奪える
- 下限難易度 × K の作業量を払える攻撃者は、偽ヘッダで窓を短縮できる（コストで守るだけ）。下限が実難易度より低すぎると守りが弱い。祖先は窓の間に見張っている必要がある
- 秘匿性：取引グラフは公開される。枠・P・祖先はハッシュでコミットし、消費時に必要分だけ明かすが、木の形とタイミングは漏れる（v0.1では隠さない）

## 判定（進む / やめる）

- 試作で、保存則・縮小則・一枝失効・回収・競合（同時使用、使用と奪還の競合、再送、古い状態）が全てスクリプト検証で通り、正当な操作も通ること
- 先行研究（ZKM・sCrypt 状態コントラクト・Bitcoin コベナント研究・UCAN/Biscuit・ERC-7710）に、同じ「途中祖先の選択的失効＋保存則つき回収を合意で強制」が既にあれば、独自発明の主張をやめ再現成果にする
- 実資金・メインネット送信・対外発表は行わない（ローカルのスクリプト検証のみ）
