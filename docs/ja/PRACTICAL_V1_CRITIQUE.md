# 実用版 v1 への実用批判

2026-11-16。対象は `docs/PRACTICAL_V1.md`（実用版）と `docs/AUTHORITY_UTXO.md`（v0.4）。実装コードは読んでいない。`npm test` は回していない。メインネット送信・対外送信・commit はしていない。条文の現行突合は「未確認」に分けた。

束＝回数・操作範囲・期限をまとめた権限。預け入れ＝その束をサービス側ゲートウェイの鍵へ渡すこと。精算＝ゲートウェイが使った回数 k をまとめて台帳から減らすこと。没収＝祖先が束を取り戻すこと。

## 結論

この仕様のままでは、チェーンに載せないと解けない場面は無い。

v0.4 が主張したのは、委任の木のどの祖先も、自分より下の1枝だけを止め、未使用枠を二重計上なく取り戻すことであり、その保存を共有管理者ではなく BSV のスクリプトと UTXO の一回消費で強制することだった。実用版は、1回ずつの消費をサービス側ゲートウェイの `node:sqlite` に移し、精算前の没収で祖先が使った分まで多く取り戻せることを自認し、争議は記録だけで自動にしない。回数が守られる場所はゲートウェイの手元台帳である。チェーンが残して守れるのは、束の総数の上限、範囲、期限、委任の形、預け先が1つであること、祖先が UTXO を動かせることまでである。

ゲートウェイが正直なら、同じ動作は次で足りる。

- 発行者（または発行者が契約した1つの枠サービス）が枠を持ち、OAuth か API キーで配る
- UCAN か Biscuit で減衰した委任を渡し、検証者は失効リストを見る
- Stripe の前払いクレジットのように、信頼する台帳がオーソリとキャプチャを分ける

ゲートウェイが不正なら、実用版のチェーンも1回ずつの呼び出しを止められない。相手がチェーンを見なければ停止も没収も届かない。精算に遅延が無いので、不正なゲートウェイは預け入れの直後に k＝束の全数を書いて枠を焼き切れる。

## 1. チェーン無しの三方式と、専用の場面

### 中央の枠（OAuth / API キー）

発行者が回数の台帳を持つ。子への分割は台帳の行を分ける。1枝だけの停止は、その行を無効にする API である。再送防止は nonce、範囲と期限はトークンに書く。落ちるのは発行者のサーバが止まったときと、発行者が台帳を改ざんしたときである。実用版は、この信頼を発行者からゲートウェイへ移している。ゲートウェイは API を動かす当事者なので回数を知っている、と仕様は書く。その信頼で足りる業務では、公開チェーンは台帳の複製である。

### UCAN / Biscuit

委任と減衰は、発行者に連絡せずトークンだけでできる。UCAN の仕様は、閉じ込めはできないと自分で書いている。下位の再委任を、委任者が全部知ることは保証できない（全プロセスがオンラインである必要があるため）。失効は別仕様で、委任の発行者が CID を無効化し、検証者が失効ストアを見る。Biscuit も、失効識別子を検証者の失効リストと照合する。トークン単体では、2つのサービスが同じ親束を同時に使ったことを止められない。

実用版の「預け先が1つ」は、UCAN の受け手（`aud`）をゲートウェイの識別子に固定するのと同じ種類の拘束である。差が残るのは、親トークンの使用済みを、どの検証者も見る共有の台帳に書くときだけである。その台帳の運営者は、発行者、相互出資の清算会社、公開チェーンのどれでもよい。公開チェーンが要るのは、参加者の全員がその1つの運営者を拒むときだけである。

未使用枠を祖先の残高へ自動で戻す機能は、UCAN にも Biscuit にも無い。実用版も、精算前の没収で戻る量が手元の消費とずれる。返還の正しさでは、実用版はトークン方式に勝っていない。

### Stripe 型の前払い

Stripe の billing credits は、メーター（呼び出し回数などの集計）に紐づく前払い残高である。台帳は追記式で、請求の確定時に残高へ充当する。顧客残高の増減は Stripe が記録する。x402（Coinbase）は、HTTP の1回の要求に支払いを載せ、オーソリのあと加盟店がキャプチャする。いずれも、祖先の秘密鍵だけで、プラットフォームの同意なく残高を動かす機能は無い。

実用版の差分はそこだけに見える。ただし精算トランザクションに作業量の遅延が書かれていない。ゲートウェイは自分の署名で k を減らせる。不正なゲートウェイが全数を先に精算すれば、祖先の鍵は空の残りを受け取る。鍵だけでプラットフォームに勝てる、という差分は、精算が即時に書ける限り閉じない。

### この形でないと解けない場面

無い。形が近い業務を3つ挙げる。いずれも、管理者つきの既存方式で回っており、実用版の「手元で数えて、あとで k を書く」では、その業務が今困っている点は閉じない。

1. 保険の委任引受。ロイズのマネージング・エージェントが、カバーホルダー（日本でいう保険総代理店に近い）へ、引受できる範囲と権限を契約で渡す。下位への再委任は、原則としてロイズの事前承認が要る。権限の範囲はバインディング・オーソリティ契約に書き、実績は報告とロイズのシステム（DCOM、ATLAS）で見る。会社の種類は、シンジケートを運営するマネージング・エージェントと、承認を受けたカバーホルダーである。痛みは「遠隔地の代理店が、報告の前に権限を超えて契約を結ぶ」ことである。実用版は、超えたかどうかの1件ずつをゲートウェイ（代理店側）が数え、精算で k を書く。報告前に枠を超える問題は、精算前の手元消費として残る。この業界は責任主体（マネージング・エージェント）を契約で残すことが要件であり、管理者のいない台帳は要件と逆向きである。

## 2. 穴と、それぞれの最小の対策

### 預け入れの待ち

実用版は、預け入れの確認数 K を束の価値で下げ、小さい束は K＝0〜1 とする。K＝0 の支出は、同じ束を2つのサービスへ同時に出す競合をチェーンが止めていない。止めるのは、後からどちらかが確認されたあとである。v0.4 は、窓の強さを BSV で K 確認を待った取引と同じだとし、REDTEAM の実測として、メインネット難易度での K＝2 の偽造コストを約135.8ドルと書いている。価値が小さいほど K を下げる規則は、束を割って K＝0 で二重に預ける抜け道になる。

最小の対策: K＝0 を禁止する。確認コストを下回る束はチェーンへ出さず、発行者の台帳に残す。チェーンへ出す束は、下限難易度を発行時点の実難易度に近い値で固定し、K は1以上で、束の価値を割るために下げない。

### 精算前の没収による過大回収

仕様が自認している。ゲートウェイが手元で m 回通したあと、精算前に祖先が UTXO を取ると、祖先は使った m 回ぶんを多く取り戻す。ゲートウェイには署名つき利用記録が残るが、v1 は自動の争議をしない。加えて、精算側に v0.4 の「使用は K ブロック待つ」が書かれていない。祖先が必ず勝つ、は使用パスの性質であり、実用版の精算には受け継がれていない。

最小の対策: 未精算の消費がある束について、祖先の没収トランザクションは全額を祖先へ戻すことをスクリプトで拒否する。没収が通るのは、精算済み（手元消費ゼロ）の残りだけにする。ゲートウェイは、停止署名を受けた直後に、溜まっている k を先に精算し、その後の残りだけを祖先が取る。自動の争議システムは作らない。これで過大回収の窓は「最後の精算バッチ」に縮む。バッチを小さくする運用は、その後の調整でよい。

### ゲートウェイの不正

仕様は、ゲートウェイが k を水増しして束の総数を増やせない、と書く。増やす攻撃は確かにスクリプトで止まる。顧客が損する方向は別で、ゲートウェイが実際の呼出より大きい k を書いて枠を焼く。停止要求とチェーン監視を無視して呼出を通し続けることも、ゲートウェイが自分で止めない限り止まらない。仕様が信頼してよいのは、正直なゲートウェイが自分の API の回数を自分のために数えることまでである。

最小の対策: 精算の k は、ゲートウェイの署名だけでは通さない。利用者（末端エージェント）の署名つき要求を k 件束ねたときだけ、スクリプトが k を減らす。ゲートウェイ単独では1も減らせない。顧客への約束は「正直なゲートウェイなら、祖先の停止署名で1枝だけミリ秒で止まる」までに限る。

### 鍵

v0.4 の通り、祖先鍵が漏れるとその下の枝を奪える。実用版では、同じ鍵で即時停止も出せる。ゲートウェイが預け入れの holder になるので、ゲートウェイ鍵が漏れると、預かった束の精算権が渡る。2-of-3 は盗難そのものを消さない、と v0.4 が既に書いている。

最小の対策: 上の精算規則（利用者署名が k 件要る）を鍵対策に兼ねる。ゲートウェイ鍵だけでは精算できない。祖先鍵は発行時の既定を 2-of-3 にし、停止署名もその閾値のままにする。末端鍵が漏れた束は、期限を切った新しい束を発行し、旧束へ停止署名を送る。漏れた祖先鍵を台帳から消す機能は作らない。

### BSV を採用する障壁

顧客のセキュリティ審査で止まりやすい事実が3つある。

- 2019-04-15、Binance は Bitcoin SV（当時のティッカー BCHSV）の全取引ペアを 2019-04-22 に廃止すると告知した。理由の列に、開発の質と、非倫理的または詐欺的な行為の証拠を挙げている。https://www.binance.com/en/support/announcement/detail/360026666152 （2026-11-16 参照）
- 2024-05-20、イングランド・ウェールズ高等法院は、Craig Wright が Satoshi Nakamoto ではないとの判決を出した。[2024] EWHC 1198 (Ch)。https://www.judiciary.uk/judgments/copa-v-wright/ （2026-11-16 参照）
- v0.4 自身が、失効窓の強さは BSV の K 確認と同じであり、それより強くはできない、と書いている。確認を束の価値で K＝0〜1 まで下げる実用版は、その同じ強さよりさらに弱い。

v0.4 が BSV を選んだ理由（大きなスクリプトでブロックヘッダを自分で検証する）は、実用版が1回ずつのヘッダ検証をやめた時点で、呼び出し経路からは外れている。残るチェーン操作は、発行、委任、預け入れ、k の減算、没収である。これは他の台帳でも書ける種類の状態遷移である。公開すると、誰が誰に何を渡したかのタイミングは残る、と v0.4 が書いている。会社間の委任は営業秘密になりうる。

最小の対策: ゲートウェイの検査インタフェースの裏で、台帳を差し替え可能にする。初期の実装は、仕様の受入条件5の通り、メモリ上のアダプタか自社の sqlite だけにする。BSV のメインネットへ接続する条件は、検証者の全員が1つの運営者を拒む契約が署名されたあと、に限る。それまでデモとテストにメインネットを出さない。

### 規制

束を金銭の対価で発行し、発行者以外のゲートウェイが提供する役務の代価に使えるなら、日本の資金決済法の前払式支払手段に当たりうる。発行者以外でも使えるものは第三者型で、登録を受けた法人でなければ発行できない（制定時要綱の第7条関係）。発行者の役務だけに使えるものは自家型で、基準日の未使用残高が政令の基準額を超えると届出が要る（同第5条関係）。基準額を超えると、未使用残高の2分の1以上の発行保証金の供託が要る（同、発行保証金の供託）。金融庁の制度説明資料は、基準日未使用残高1,000万円超を届出・供託の閾値として図示している。2026-11-16 時点の e-Gov 現行条文と政令額は、この批判では突合していない。

不特定の相手との売買や移転ができる支払手段にすると、暗号資産側の規制（交換業の登録、またはその後の業規制）に入りうる。金融庁の2024事務年度の監督概況は、前払式支払手段と暗号資産交換業を別々に監督対象として数えている。2026年に暗号資産規制が金商法へ移ったか、移ったとしていつ施行かは、一次資料で未確認である。Wikipedia の記述は採用しない。

公開台帳に会社名、担当者、エージェントの識別子を書くと、消せない記録になる。EU の顧客を含むなら、GDPR の保存制限と消去（規則 2016/679）と衝突する。

最小の対策: 実用版の束は、対価を取らず、発行者自身と、1つの契約先のゲートウェイの中だけで使う認可回数に限る。売買、譲渡、払戻しを仕様で禁じる。satoshi は送付に必要な最小にする。公開するのはコミットメントだけで、会社名と操作の中身は載せない（v0.4 が既に、枠・範囲・祖先はハッシュでコミットする、と書いている）。対価を取る設計に変える前に、弁護士へ現行条文の確認を渡す。この確認は本人判断である。

## 3. 最初の顧客と、最初のデモ

最初に金を払いうる相手の型は、次である。

日本の受託、BPO、または AI の運用代行で、従業員がおおよそ20人から200人。1本の上流 API キー（模型、検索、顧客の基幹）を、複数の顧客案件と複数のエージェントで共有している。1体が暴走すると、同じキーの枠を他の顧客ぶんまで溶かす。セキュリティ審査があり、暗号資産の新規採用は通らない。欲しいのは「悪い子だけ、今すぐ止める」ことである。BSV で保存則を強制したい、とはまだ言っていない。

この型の痛みは、中央の枠と即時の失効で解ける。それでも最初の支払いが起きるのはこの型だけである。コンソーシアム（清算会社を作りたくない同業者グループ）は、第1節の (c)(d) を仕様が満たしてからでなければ売り物にならない。

最初に見せるデモは1場面だけにする。

会社Aが1000回の束を持つ。Bの子エージェントが2体いて、それぞれがモック API を叩いている。親が子1だけに停止署名を送る。子1の次の呼出は拒否され、子2の呼出は通り続ける。画面に出すのは、判定時間の p99（目標は仕様の5ミリ秒未満）、子1が止まったこと、子2の残数が減り続けること、である。txid、確認待ち、ウォレット、円換算は出さない。台帳はメモリ上のアダプタでよい（受入条件4の範囲）。

視聴者が「API キーを2本に分けただけと同じ」と言ったら、その場では同意する。実用版で本当に見せられるのは、正直な1つのゲートウェイが、祖先の署名で1枝だけ止めることまでである。止めたい枝を、協力しない別サービスからも回収する場面は、このデモに入れない。それは未実装であり、第1節の結論と矛盾する。

## 判定

実用版は、v0.4 の「1回ごとに K ブロック待つ」を手元のカウントで避けた。その代わり、v0.4 が管理者なしで強制すると主張した保存則と祖先優先は、ゲートウェイの正直さと、精算前に没収しない運用へ戻っている。作るなら、売り物はゲートウェイと、1枝だけの即時停止である。BSV は受入条件5の通り、外へ出さない。チェーンが必須の顧客は、この文書の時点ではいない。
