# 権限コベナント赤チーム（2026-11-16）

対象は `feat/authority-utxo` の `bad06da`、`authority/lib/cov/*.mjs`。評価は `@bsv/sdk` の `Spend.validate` だけ。取引は送っていない。BSV ノードは動かしていない。

## 結論

v0.2 の「遅延中は祖先が確定的に勝つ」と、期限 T で権限が終わる、はスクリプトが強制している形では偽である。スクリプトは nLockTime を整数として `U ≤ L ≤ T` と比べ、保有者の使用と委任に 600 を足す。Genesis 後のコンセンサスでは、その整数は 500,000,000 未満ならブロック高、以上なら Unix 時刻であり、満たしたあとも「以後は無効」にはならない。500,000,000 は 1985-11-05 の時刻なので、ブロック高として将来にある U でも、ここへ飛び越えれば今すぐ確定する。

枠の水増し、P/T の拡大、祖先の偽装、接頭辞の穴、余分な入出力、satoshi の抜き取り、sighash と preimage の改変、非最小エンコード、負のゼロは、今回の反例では拒否された。

## 破れた攻撃

深刻度は、権限の二重使用を合意で止めるという主張に対するもの。

| 試験 | 深刻度 | Spend.validate | 何が通ったか |
|---|---|---|---|
| X01 期限後でも使用が通る | 致命 | ok | T=1,600,000,000（2020-09-13）の UTXO を L=1,599,999,601 で使用。枠 2→1。出力 U=1,600,000,201 |
| X02 過去タイムスタンプの梯子 | 致命 | ok が 3 連続 | U=1,500,000,000、枠 3 を使い切り。各 L は 1,510,000,000 未満。隣同士の差は 600 以上 |
| X03 ブロック高 U の読み替え | 重大 | ok | U=50,000,000 を L=500,000,000 で使用。出力 U=500,000,600 |
| X04 試験定数 U=1,000,000 | 致命 | ok が 2 連続 | 1 回目 L=500,000,000、2 回目 L=500,000,604 で枠 0。どちらも 600,000,000 未満 |
| X05 未来時刻の梯子 | 致命 | ok が 3 連続 | U=1,900,000,000 から枠 3。全 L は 1,900,000,000 以上 1,910,000,000 未満。差は 600 以上 |
| X06 高位ビットの U | 重大 | ok | 生の U=2,524,608,000（2050-01-01、BIN2NUM では負）を L=1,760,000,000 台で使用。枠 2→1 |
| X07 使用と奪還が両方通る | 致命 | 両方 ok | U=1,000,000 の根を L=500,000,000 で委任。子に対し保有者の使用と祖先の奪還（L=0）がどちらも成功 |
| X22 負の深さ | 低 | ok | 生の d=0x80000001（スクリプト数値 -1）を委任すると子の d=0 |

X01 の実測は、同じ `spendUse` を別プロセスで走らせた値。試験本体は「1,590,000,000 より大きく T 以下」だけを固定している。この 1 回の出力 U は T を超えるので、同じ端から次は出せない。期限後に枠を使い切るには、区間 `[U, T]` の下の方を選ぶ。X02 がそれである。T は署名者が選ぶ nLockTime の上限であり、壁時計の締め切りではない。区間内の過去時刻は、一度条件を満たすと掘られ続ける。

X02 と X04 では、数値の +600 は付いている。全部が 1985〜2017 年の時刻なので、2026-11 のノードでは到着した時点で確定しており、ブロックをまたぐ待ちは無い。子孫の txid は放送前に計算できる。枠の消費を 1 ブロックにまとめられる。

X03 の U=50,000,000 は、ブロック高として読むと現行高（後述、約 97.6 万）のずっと先である。500,000,000 以上は Unix 時刻なので、同じ整数が 1985 年として今すぐ掘れる。X04 はリポジトリの試験が使う U=1,000,000 でも同じ飛び越えが通り、2 回目まで 1985 年の時刻で枠がゼロになる。

X05 は今は掘れない。1,900,000,000 は 2030 年付近で、MTP が最後の L を超えてから有効になる。有効になった瞬間、3 本とも確定している。S01 のとおり、出力 U の 1 秒前はスクリプトが拒否する。開いているのは「確認をまたぐ 600 秒」ではなく「署名時点で全部作って、最後の時刻にまとめて出す」道である。

X07 は、遅延の窓が空かないことを同じ UTXO で示している。SDK は二重消費をmempoolとして裁かない。ノードは高々一方を入れる。どちらが入るかは、両方の lockTime が既に満たされているときの先着とマイナーの選択になる。祖先が必ず勝つ、にはなっていない。

X06 は創世出力だけの穴である。状態の U を符号付きで検査していない。正直な遷移は P19 で閉じており、`OP_4 OP_NUM2BIN` が 2^31 以上を 4 バイトに書けず失敗する（規則名は直前の印 `nLockTime<=T` に寄る。実測の L=2,147,483,249、エラーは NUM2BIN のサイズ不足）。

X22 も創世出力だけである。正直な委任は d を 0 から 1 ずつ増やす。負の d を手で置くと `-1 <= 7` と `-1+1 = 0` が通り、子は奪還できない（k は 1 以上かつ d 以下）。枠は増えていない。発行者が自分の奪還を消す形で、受け取った側は状態の 4 バイトを見れば分かる。

根拠にしたコンセンサス（ノード未実行）は Genesis 仕様である。nSequence が 0xffffffff の入力は最終で、nLockTime を見ない。それ以外は、nLockTime が 500,000,000 未満ならブロック高、以上なら直近 11 ブロックの MTP が nLockTime 以上のとき最終。BIP68 は無効、CLTV と CSV は NOP。出典: [genesis-spec.md](https://github.com/bitcoin-sv-specs/protocol/blob/master/updates/genesis-spec.md)（nLockTime / nSequence の節）。

現行高の二次情報: Coin Dance は 2026-11-15 時点で高さ 975,638 を表示している（https://sv.coin.dance/）。1,000,000 未満であり、50,000,000 にも 500,000,000 にも届いていない。

## 防げた攻撃

いずれも `ok === false`。括弧は落ちた規則。

- 枠の水増し: 子を両方 `0x7fffffff` にしても合計で拒否（P01 `delegate:sum<=n`）。32 ビットのラップは起きていない。奪還で n / P / T を増やす出力も拒否（P13 `hashOutputs`）。
- P の拡大: 範囲内の余分なビット（P02 `delegate:PAsubset`）。高位ビット `0x80000001` も同じ規則（P02b）。
- T の拡大: P03 `delegate:TA<=T`。
- 祖先の偽装: 祖先でない鍵（P04 `reclaim:chain=R`）。
- 接頭辞の穴: 深さ 2 の中間鍵を空にする、または別の鍵に差し替える（P05 同じ規則）。
- 同一取引の 2 本目: ダミーの 2 本目入力で拒否（P06 `single-input`）。2 本目が別の権限 UTXO でも hashPrevouts は一致しない。
- satoshi: 1 satoshi を抜いて余り出力にする、出力を 1000 satoshi 水増しする（P07 `hashOutputs`）。入力額を超える指定（P07b `delegate:value`）。負の引数（P22 `delegate:value`）。
- 保有者の nSequence=`0xffffffff`: 未来の U でも拒否（P08 `nSequence`）。lockTime を無視して即時最終にはできない。
- sighash: ユーザー署名の末尾 `0xc1`（ANYONECANPAY|ALL|FORKID）と `0x03`（SINGLE）を拒否（P09 `sig:sig`）。検査は CHECKSIG より前。preimage 側の型は構築時から `0x41` 固定。
- preimage の 1 バイト改変: P10 `pushtx`。
- コードの差替え、余り出力: P14 `hashOutputs`。
- 深さの上限: P15 `delegate:depth<=DMAX`。
- 非最小エンコードの枠 `0100`: P18 `delegate:nA>=0`。
- 負のゼロ `0x80`: P20。規則は `delegate:value`、エラーは `non-minimally encoded script number`。hashOutputs には到達しない。値の水増しにはなっていない。
- unlock の `OP_CODESEPARATOR`: P21。SDK は「Unlocking scripts can only contain push operations」で拒否。規則名はロック側に付かない。
- 未来の Unix 時刻の順序: 使用のあと、出力 U の 1 秒前は拒否（S01 `U<=nLockTime`）。U=1,900,000,000 は 500,000,000 では使えない（P11 同じ規則）。

R01 は防御の失敗ではない。奪還は nSequence を見ないので `0xffffffff` でも通る。設計どおり。下の置換の話の材料。

## 判定不能

- ノードは動かしていない。上の「今すぐ掘れる」は Genesis 仕様と、2026-11-15 の公開高からの読みである。SDK は MTP も mempool も見ない。
- 置換による緩和は未検証。仕様では、未確定の取引は、入力が同じ順で、新しい nSequence が全部以上かつ 1 つは大きいとき、置換が必須になる。保有者の使用は `0xfffffffe` 固定（P08）。奪還は `0xffffffff` で通る（R01）。保有者が未確定のまま先に放送していれば、祖先の最終奪還が仕様上は置き換わる。保有者が lockTime を満たしてから出せば、到着時点で最終であり、この置換は使えない。500,000,000 への飛び越えには未確定の期間が無い。
- 手数料は 0 になる。使用と奪還は入力の 8 バイトをコピーし、委任は金額の和を入力に一致させ、余りは 0 satoshi の OP_RETURN。単一入力なので手数料を載せる入力が無い。0 手数料をマイナーが入れるかはポリシー。
- 499,999,999 は試験していない。仕様上はブロック高モードで、現行高では入らない。スクリプトがこの整数を受け入れることと、ノードが掘ることは別である。
- SDK とノードで数値や CHECKSIG の subscript がずれる可能性は、今回「SDK だけが攻撃を通した」形では出ていない。P01 は巨大な和を拒否した。正直な使用が SDK で通っているので、PUSH_TX の合成署名がノードだけ拒むなら、起きるのは偽の受け入れより正直な取引の停止である。未実行。
