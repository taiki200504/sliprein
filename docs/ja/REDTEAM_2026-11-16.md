# RED TEAM — Authority UTXO v0.1

2026-11-16。対象は `AUTHORITY_UTXO.md` の次の主張。ローカルの反証メモであり、実装の証明でも対外発表でもない。スクリプトの実行、チェーンへの送信、commit はしていない。一次資料は同日に取得した本文。回路や契約バイトコードは動かしていない。

> 委任の木のどの祖先も、自分より下の1枝だけを、他の枝を止めずに失効させ、その未使用枠を二重計上なく自分へ回収できる。この保存則（発行量 = 消費 + 破棄 + 未使用）と縮小則（子 ⊆ 親）を、共有管理者ではなく BSV のスクリプト検証と UTXO の一回消費で強制する。

## 結論

この文章のままでは、主張は成立していない。分割について書かれた検査は、回収取引には書かれていない。回収出力の枠・権限ビット・期限・祖先リストをスクリプトが縛る、という強制はまだ仕様に無い。加えて、保有者と祖先が同じ出力を取り合うとき「先に確定した方だけが有効」とする規則は、祖先が枝を失効できることを保証しない。台帳上の一回消費は、外部APIの一回実行を作らない。

部品は既出である。公開BSV上で、satoshiとは別の整数枠を、伸びる祖先リストの1鍵が1出力だけ回収する、という未実装の組合せだけが残る。それを新規発明として進める根拠にはならない。

## 2. 攻撃

各項は、主張のどの文を壊すか、対策か原理的な限界か、を付ける。対策は「こう書けば脚本が通り得る」であって、書いたことにはならない。

### 2.1 祖先鍵の盗難

祖先 i の鍵で対象UTXOを消費できる、という経路がそのまま盗難経路になる。盗まれた鍵の下は、兄弟を含む全部の未使用枠を回収できる。仕様はこれを残る信頼として書いている。主張の「どの祖先も失効できる」は、その鍵の所持者と鍵の盗難者を区別しない。

回収取引が権限ビットを広げられる実装だと、盗難は残高の移動を超えて、根より広い権限の鋳造になる。

対策: 祖先鍵はしきい値にする。回収出力にも縮小則と接頭辞規則（2.6）を掛ける。盗難そのものを脚本で消すことは原理的に無理である。失効できる主体は、その主体になりすました署名でも失効できる。

### 2.2 使用と奪還の競合

仕様は「先に確定した方だけが有効」と書く。これは Bitcoin の二重使用規則であり、祖先が勝つ規則ではない。保有者は、奪還を見たら同じ出力を自分宛へ移す取引を先に確定させられる。移した先の脚本が祖先を残すなら、祖先は次の出力を追い続ける。保有者が毎回先に確定させる限り、失効は終わらない。主要なマイナーが保有者側を採るなら、祖先は勝たない。

兄弟枝のUTXOに触らないことと、対象枝を止められることは別である。この競合は後者を壊す。

対策: 金庫と同じ非対称にする。保有者の消費と再委任には相対遅延を課し、祖先の回収には遅延を付けない。遅延中だけ祖先が確定的に回収できる。BIP-345 が書いているのはこの非対称である。原理的に無理ではない。今の「先着」の文面では主張は偽である。

BSV ではこの遅延を OP_CSV に置けない。Genesis の解説は、OP_CHECKLOCKTIMEVERIFY と OP_CHECKSEQUENCEVERIFY を NOP に戻したと書く（[Genesis upgrade](https://hub.bsvblockchain.org/wiki/blocks-and-the-blockchain/blockchain/genesis-upgrade)）。2026-11-16 に取得した [opcodes.md](https://protocol.bsvblockchain.org/specification/opcodes.md) の範囲には、この2つの有効化行は無かった。遅延は preimage の nLockTime / nSequence を脚本が検査する形で書く。opcode がある前提の移植は空振りする。

### 2.3 0-conf の二重使用

保有者が使用取引をサービスに見せ、対立する回収か別使用をマイナーに入れる。サービスが未確定取引で仕事をすると、台帳の枠は片方にしか残らないのに、仕事は既に終わっている。逆に、回収が先に見えて枠が戻ったあと、使用側が再組織で生き返ると、戻した枠と実行が両方残る。

対策: サービスの実行は、脅威モデルに書いた確認深さの後だけにする。0-conf を禁止すればこの項は閉じる。即時実行と即時失効を同時に保証することは、研究課題の「原理上の境界」どおり無理である。

### 2.4 サービスが確定前に実行する、および確定後も一回にならない

仕様の「残る信頼」は正しい。ここを残したまま「合意が権限の二重使用を止める」とは言えない。壊れ方は3つある。

- 未確定の消費を見て実行する。
- 確定した同じ消費証明を、宛先の違う2つのサービスが両方受理する。消費取引にサービスの識別子が縛られていない。
- 実行したあと、nullifier を書く前にプロセスが死ぬ。再送でもう一度実行する。台帳は既に1回消費済みなので、2回目を拒む材料は台帳に残っていない。

対策: 消費出力にサービス公開鍵を1つだけ書かせ、各サービスは自分宛の証明だけを採る。nullifier はサービス側の共有台帳に、実行より前に予約する。確認前は実行しない。

外部APIが取引に署名も出力も出さないなら、台帳の消費とAPIの作用を一つの原子操作にすることは原理的に無理である。サービスが脚本の当事者になり、自分の署名が無い使用を無効にするところまで入れて、初めて窓が「予約と実行の間」に縮む。窓はゼロにならない。

### 2.5 コベナント実装で保存則と縮小則が抜ける

OP_PUSH_TX は「この交易を見られる」だけである。保存則は、見た結果に対する検査を全部書いたときにだけ成立する。v0.1 が分割について書いているのは、子の合計 ≤ 親、ビット積、期限、同じ脚本型、祖先リストへの追記、である。回収については「祖先の署名と包含証明で消費し、祖先の権限UTXOへ戻す」としか無い。戻し先の枠・ビット・期限・祖先リスト・出力本数の検査が無い。この経路が主張の本体なので、強制の文は今は偽である。

脚本でありがちな抜けは次のとおり。

- sighash が `SIGHASH_ALL | SIGHASH_FORKID`（0x41）以外だと、preimage の hashOutputs や hashPrevouts が零になり、出力や他入力を縛れない（[preimage の実測表](https://raw.githubusercontent.com/codenlighten/smartledger-bsv/HEAD/docs/preimage.md)）。
- hashOutputs との一致を第1出力だけに掛けると、余り出力に枠を複製できる。sCrypt のカウンタ例が全出力ハッシュを見ているのは、このためである。
- 検査が `各子 ≤ 親` だと、子が2人いるとき合計が親を超える。主張の等式は `合計` である。
- 合計をスクリプト整数で足すとき、桁あふれや符号ビットで小さい値に見える。範囲を先に固定しないと等式は抜けられる。Genesis 以降、数値の合意上限は大きい（750,000バイト、Chronicle ではさらに大きい）が、大きいことと検査したことは違う。
- 手数料用の第2入力が別の権限UTXOだと、今の入力の脚本からは相手の枠状態が見えない。preimage は自分の scriptCode しか持たない。片方の脚本だけが「出力枠 = 自分の枠」を見ると、もう片方の枠は消えるか、出力を合計に盛ると水増しになる。
- コード部とデータ部の切り方がずれると、次出力のコードを差し替えられ、以後の検査が消える。
- `P_child AND P_parent == P_child` は、P がスクリプト数値のビット集合であるときにだけ意味を持つ。P が文書のハッシュなら、この式は縮小ではない。OP_AND はバイト列一般の部分集合検査ではない。
- 期限 0 を「無期限」と読むと比較が逆転し、子の方が広くなる。高さ時刻と UNIX 時刻を同じ整数で比べると縮小にならない。

対策: 権限入力は1本。手数料は同じUTXOの satoshi から払うか、枠を持たない定型入力だけを許す。枠は satoshi と別フィールドにする。権限出力の枠合計 + 明示破棄 = 入力枠。破棄出力は権限脚本であってはならない。コード部はバイト単位で固定する。sighash 型を 0x41 に固定する。これは原理的に無理ではない。書いていない回収経路に、この検査はまだ無い。

### 2.6 祖先リストの包含証明

「リストのどこかに鍵がある」だけでは、兄弟の鍵や、保有者が後から足した鍵を祖先として通せる。回収後のリストを切らないと、失効した子の鍵が回収出力の祖先のまま残り、子が回収枠をすぐ奪い返す。

ハッシュ連結だけのコミットは、葉と内部節のドメインが同じ Merkle 証明で、内部節を葉として通せる。追記が「署名した鍵を末尾に1個」ではなく「証明者が見せた列」だと、途中への挿入と祖先の削除ができる。削除ができると、根はその枝を二度と回収できない。

対策: 委任は `R' = R || この取引の署名鍵` の再計算と一致だけを許す。回収出力の R は、署名者までの接頭辞だけにする。Merkle にするなら葉タグを分ける。原理的に無理ではない。v0.1 は包含証明と書いて、接頭辞と回収後の切断を書いていない。

### 2.7 プライバシー漏れ

研究課題の4条件には「検証者へ全委任履歴を公開しない」がある。この設計は取引グラフと時刻を隠さない、と自分で書いている。それより強い漏れが、失効の仕組み自体から出る。

祖先が署名して特定の出力を消費すると、その公開鍵とその枝が台帳に残る。使用時に祖先リストを開いて包含を示すと、開いた祖先が公開される。状態を locking script の末尾に置く sCrypt 型は、枠と権限ビットが未使用の間も見える。

ZKM 仕様 §7 は、ホップごとの失効ハンドルを検証者が引ける場所に登録すると、そのハンドルが系統そのものになる、と書く。透明な脚本で「どの祖先がどの出力を署名で殺したか」を隠しつつ失効するのは、裸の BSV スクリプトでは原理的に無理である。隠すなら ZK 検証を脚本に載せるか、失効ハンドルを ZKM v2 のように別の蓄積器へ入れる。どちらもこの v0.1 には無い。隠さないと決めるなら、研究課題の4番目は落としたと書く。隠せると書かない。

### 2.8 BSV 固有

- 合意の前提が薄い。2021年6月から8月に、ブロックの保留と再組織、二重使用を狙った隠し鎖が観測されている（[Bitcoin Association の説明](https://bsvblockchain.org/on-the-white-paper-view-of-hidden-chains-and-double-spends/)、[CoinGeek の FAQ](https://coingeek.com/faqs-july-2021-block-withholding-re-organisation-attack-on-the-bsv-network/)）。数確認の SPV を最終と扱うと、回収も使用もひっくり返る。
- 未確定取引の txid は unlocking script の可鍛性で変わる。子の委任が親の txid を指していると、親が確定する前の子はまとめて無効になる。これは 2.9 と重なる。
- ファーストシーンはリレー方針であり、合意ではない。マイナーは競合のどちらでもブロックに入れられる。手数料の高い方が勝つ、という Bitcoin Core の経験則はここでは使えない。
- Genesis で P2SH が無効、CLTV / CSV が NOP。BTC の vault 教程の opcode はそのまま動かない。
- トランザクション評価の標準方針には時間切れがある（Genesis 解説は既定1秒）。祖先リストを脚本ループで毎ホップ検証する深い木は、リレーされず、事実上失効も使用もできない枝になる。

対策: 委任も失効も、対象出力が脅威モデルの深さまで確定してから組む。タイムロックは preimage 検査。深い確認の後も、再組織で外部作用が二重化し得ることは残る。PoW の上で「覆らない」と言うのは原理的に無理であり、深さと経済コストで縛るだけである。

### 2.9 未確定の親を替えると兄弟も死ぬ

分割直後、2つの子は同じ未確定の親にぶら下がる。親を対立取引で取り替えると、両方の子が消える。この窓では「1枝だけ失効し、他枝は止めない」が成り立たない。確定後の出力は独立なので、窓は未確定の間に限られる。

対策: 親が所定の深さまで確定してから、その出力を子へ分ける。失効も確定済み出力だけを対象にする。原理的に無理ではない。

### 2.10 等式でない保存と、回収の二重計上

主張の保存則は等式である。仕様の分割検査は `≤` である。差は破棄として出力に残らないので、観測者は「発行 = 消費 + 破棄 + 未使用」を台帳から再計算できない。差を後の取引で別の枠として見せる実装バグと、正当な焼却が区別できない。

台帳の外では、サービスが使用を計上したあとに回収が確定すると、同じ枠が「消費済み」と「祖先の未使用」の両方に載る。これは 2.4 の会計版である。UTXO は1回しか消費されないので、台帳の中だけでは二重にはならない。主張が「二重計上なく回収」と言うとき、台帳内だけを指すなら 2.5 の検査が揃った後に限り真であり、サービス側の勘定を含むなら 2.4 のとおり偽である。

対策: 等式と明示破棄。サービス勘定は台帳の外だと書いて、回収が外部作用を取り消さないと書く。外部作用の取り消しは原理的に無理である。

## 3. 新規性

**部分的に新しい。**

ZKM v0.1.0-draft rev 12 は、枠の保存、縮小、分割、同一ノートの一回消費を既に規範へ書いており、途中祖先の失効は未着手と自分で書いている。その将来案は権限を殺すハンドルであり、未使用枠を祖先へ戻す遷移ではない。

UCAN、Biscuit、ZCAP-LD は、鎖の途中から下だけを無効にし兄弟を残す失効を既に定義している。強制は失効リストか検証者の状態であり、未使用枠の回収は無い。BIP-345、CTV 金庫、Ark の葉は、コインの回収と「他の出力を巻き込まれずに扱う」ことを既に定義している。対象は権限ビットではなく satoshi である。

残る差は、公開の BSV 脚本で、satoshi と別の整数枠を、伸びる祖先列の1鍵が1出力だけ回収する、という組合せが、今回読んだ仕様のどれにも完成形で無いことだけである。組合せが未掲載であることと、脚本がそれを強制していることは別であり、後者は v0.1 ではまだ偽である。
