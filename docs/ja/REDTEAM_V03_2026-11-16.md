# 権限コベナント v0.3 赤チーム（2026-11-16）

対象は `feat/authority-utxo` の `005498d`、`authority/lib/cov/*.mjs`。評価は `@bsv/sdk` の `Spend.validate` だけ。取引は送っていない。BSV ノードは動かしていない。既存ファイルは変更していない。

## 結論

v0.3 の「予告中は祖先が奪還でき、確定には K=2 の作業量が要る」は、出荷している下限では窓にならない。スクリプトの作業量ターゲットは `ff`×30 + `0000`（2^240−1）で、ヘッダの bits・前ブロック・時刻の新しさは見ない。メインネットの bits `0x18225459` を書き、前ハッシュを 32 バイトのゼロ、時刻を 1 にした自作ヘッダ 3 本で、使用の確定が通った。同じ予告に対する祖先の奪還も通った。ノードは高々一方しか掘らない。どちらが入るかは先着とマイナーの選択で、祖先が先に動ける時間は無い。

この定数の弱さは `docs/AUTHORITY_UTXO_V03_RESULT_2026-11-16.md` が既に書いている。今回はそれを `Spend.validate` の反例と、実測の試行回数にした。

枠の水増し、出力の並べ替え、破棄出力への satoshi 移動、コード差替え、64 バイトの Merkle 兄弟、誤った index、再予告、低 S のための nLockTime 変更は、今回の反例では拒否された。

## 破れた攻撃

深刻度は「予告中に祖先が確定的に勝つ」に対するもの。satoshi の持ち出しと枠の増加は起きていない。

| 試験 | 深刻度 | Spend.validate | 何が通ったか |
|---|---|---|---|
| R2-A 偽の浮遊ヘッダで確定 | 致命 | ok | h0 の前ハッシュは全ゼロ、Merkle 根は予告 txid だけ、時刻は 1、bits は `0x18225459`。3 本ともハッシュは 2^240−1 以下かつメインネットターゲットより大きい。枠 3→2、phase は 0。実測の nonce 試行は 56,653 / 40,720 / 66,627、合計 164,000。locking script 3,237 バイト、unlocking script 3,738 バイト。確定の nLockTime は 1 |
| R2-E 確定と奪還が両方通る | 致命（R2-A とセット） | 両方 ok | 同じ予告 UTXO に、保有者の使用確定（枠 2）と親の奪還（枠 3、phase 0）が両方成功。後継 txid は別。合意では高々一方 |

R2-A の否定対照は、h0 の nonce だけを動かしてハッシュを 2^240−1 より大きくしたもので、`headers:work` で落ちた。作業量検査そのものは常時成功ではない。h2 の時刻を `0x80000000` にすると `headers:expiry` で落ちた。符号ビットで期限検査を飛ばす道は、この値では開いていない。

### (a) 金額

二つの数字を分ける。

**このスクリプトに対するコスト。** 期待試行はヘッダあたり 2^16 = 65,536 回の SHA256d、K+1 = 3 本で 196,608 回。今回の 1 本の鎖は 164,000 回で、スイート全体は 2.0 秒だった。報酬換算は 0 ドル。bits 欄にメインネットの値を書いても、スクリプトは bits を読まない。採掘後に bits を書き換えるとハッシュが変わり、作業量検査も落ちる。時刻 1 は T=2,000,000,000 以下なので期限も通る。

**下限を高さ 975,655 のメインネットターゲットに置き換えたときの報酬換算。** これは反実仮想で、今のスクリプトのコストではない。偽造は 3 ブロック分の採掘に相当する。

## 防げた攻撃

いずれも `ok === false`。括弧は落ちた規則。

- Merkle（R2-B）: 葉が予告 txid、兄弟 2 段の index 0 は通った。同じ証明の途中に空兄弟を挟んでも通った（空は段を消費しない）。index 1、index 2、兄弟を 1 個だけにしたもの、64 バイトを 1 個の兄弟にしたもの、64 バイトの `0xab` は拒否（`merkle`）。
- intent（R2-C）: 手書きの出力直列化は `intentHash` と一致した（使用と委任の両方）。コードを `OP_DROP OP_1` に差し替える hashOutputs を予告してから確定すると拒否（`hashOutputs`）。0 satoshi の権限出力と、全額を載せた OP_RETURN の組も拒否（`hashOutputs`）。正直な委任 intent のあと、出力の入れ替え、1 satoshi への減額、破棄出力の削除、使用パスへのすり替えは拒否（`confirm:intent`）。入れ替えた並びの hashOutputs を最初から予告し、その並びで確定しても拒否（`hashOutputs`）。
- 予告の操作（R2-D）: 予告中の再予告は拒否（`announce:phase`）。保有者自身の奪還は拒否（`reclaim:chain=R`）。親の奪還は通り、枠は 3 のまま、phase は 0。満たせない intent `ab`×32 の予告は通るが、確定は `confirm:intent`、発行者の奪還は `reclaim:k<=d` で落ちる。枠は増えない。発行者が自分の UTXO を止めるだけで、深刻度は低。子を両方 `0x7fffffff` にした委任の確定は拒否（`delegate:sum<=n`）。32 ビットのラップは起きていない。
- 低 S の nLockTime（R2-F）: 予告の lockTime は 1（探索幅 0 以上 400 未満）。確定を 500,000,000 から始めても、偽ヘッダが正しければ通り、実際の lockTime は 500,000,000 以上 500,000,400 未満。別の Merkle 根で掘ったヘッダは `merkle` で落ちた。v0.2 の 500,000,000 は、ヘッダ結合も期限も外さない。スクリプトは nLockTime を読まないので、この調整は新しい認可にもならない。

## 判定不能

- ノードは動かしていない。3,237 バイトと 3,738 バイトが合意や既定ポリシーの上限に当たるかは、Genesis 仕様とサイズの比較だけである。出典: [genesis-spec.md](https://github.com/bitcoin-sv-specs/protocol/blob/master/updates/genesis-spec.md)（2020-01-09 版の raw）。スクリプト要素サイズとスクリプトサイズの合意上限は削除され、取引サイズの合意上限は 1GB（1,000,000,000 バイト）。既定ポリシーの最大取引は 10MB、評価タイムアウトは 1 秒（確定ブロックの再評価には適用しない）、数値のポリシー長は 250,000 バイト、スタックメモリの既定は 100MB（要素ごとに 32 + サイズ）。数値の合意上限は 750,000 バイト。3,237 と 3,738 はこのどれよりも小さい。preimage は 1 要素で旧来の 520 バイトを超えるが、その合意上限は削除済み。実ノードの設定値と、この機械での 1 秒タイムアウトは未測定。SDK の 1 回の確定は採掘込みで 7〜317 ミリ秒だった。
- SDK とノードのインタプリタ差は未実行。偽ヘッダの受理はスクリプトが bits とチェーン所属を見ない結果で、SDK だけが緩いという形ではない。SDK は手数料、ダスト、mempool、MTP を見ない。今回の確定は nLockTime=1 かつ、R2-A では nSequence=`0xffffffff`。仕様上、全入力の nSequence が `0xffffffff` なら lockTime に関係なく final。`0xfffffffe` でも lockTime=1 はブロック高で、現行高は 1 以上なので final。どちらも未確定の置換規則（全 nSequence が以上かつ 1 つは大きい）の対象にならない。mempool 上の先着は未検証。
